Sandbox de Terminal, Políticas de Permisos y Tareas en Segundo Plano

1. ¿Qué es el Terminal Sandbox y cómo protege tu ordenador?

Una duda muy lógica cuando empiezas a usar agentes que ejecutan comandos en la terminal es: "¿Y si el agente se equivoca de comando y borra algo de otra carpeta de mi ordenador?". Para que puedas trabajar con total tranquilidad y sin tener que aprobar manualmente cada mínimo comando, Antigravity ejecuta los comandos dentro de una Caja de Arena segura (Terminal Sandbox):

Figura 1. Funcionamiento del Terminal Sandbox, control de permisos y ejecución de tareas asíncronas en segundo plano.
  1. Modo Sandbox Estándar (Activo por defecto — BypassSandbox: false): Dentro del Sandbox, los comandos tienen permiso de lectura y escritura únicamente dentro de la carpeta de tu proyecto actual, en la carpeta de artefactos y en /tmp, y no tienen acceso a internet ni al resto de archivos privados de tu ordenador. Gracias a este aislamiento, el agente puede ejecutar pruebas, validar JSONs o listar archivos automáticamente sin interrumpirte para pedir permiso.
  2. Salir del Sandbox (BypassSandbox: true — Con tu permiso explícito): Si un comando concreto necesita obligatoriamente conectarse a internet (por ejemplo, para descargar paquetes con npm install o hacer git push) o levantar un puerto de red, el agente solicita ejecutar únicamente ese comando fuera del Sandbox y Antigravity te muestra un aviso claro para que lo apruebes.
  3. Aprobación Inteligente por Prefijo ("Always Allow"): Cuando apruebas un comando con la opción "Permitir siempre" (por ejemplo, apruebas npm test), Antigravity recuerda ese prefijo binario para que futuras ejecuciones de npm test ... no vuelvan a preguntarte.

2. Configuración de Permisos y Políticas (Global vs Por Proyecto)

Desde el panel de Settings (Ajustes) de Antigravity (o con el comando /permissions) puedes personalizar el nivel de autonomía del agente tanto de forma global (para todo tu ordenador) como de forma específica para un proyecto concreto:

Ajuste / Política Opciones disponibles Qué controla
Tool Execution Policy proceed-in-sandbox, request-review, always-proceed, strict Define si los comandos de terminal se ejecutan solos dentro del sandbox, si piden siempre confirmación o si avanzan automáticamente.
Non-Workspace File Access allow, ask, deny Controla si el agente puede leer o editar archivos que estén fuera de la carpeta raíz de tu proyecto.
Internet Access Policy allow, ask, deny Controla si el agente puede realizar peticiones de red a internet.
Command Allowlist / Denylist Lista de comandos permitidos o bloqueados Te permite definir comandos de terminal que siempre están permitidos sin preguntar o que están terminantemente prohibidos.
Browser Allowlist Lista de dominios web Restringe a qué páginas o dominios puede navegar la herramienta de navegador del agente.
Artifact Review Mode always-proceed, agent-decides, asks-for-review Controla cuándo se detiene el agente para pedirte que revises un Artefacto (como un plan) antes de continuar.

3. Tareas en Segundo Plano (Background Tasks), Daemons y Despertar Reactivo

¿Qué pasa cuando el agente necesita arrancar un servidor web local (que se queda encendido indefinidamente) o ejecutar una batería de tests o un build de Docker que tarda varios minutos? En Antigravity el agente no se queda "congelado":

  • Paso automático a Background (WaitMsBeforeAsync): Si un comando tarda más del tiempo de espera inicial, pasa automáticamente a ejecutarse como una Tarea en Segundo Plano (Background Task) que puedes consultar o detener en cualquier momento con el comando /tasks.
  • Procesos Daemon (IsDaemon: true): El agente puede arrancar servidores de desarrollo (npm run dev), túneles o vigilantes de archivos (watchers) en modo Daemon para que sigan corriendo indefinidamente en segundo plano mientras él continúa programando.
  • Despertar Reactivo (Reactive Wakeup): Ni tú ni el agente tenéis que estar haciendo bucles de espera (polling) para saber si un comando largo o un subagente ha terminado. En cuanto la tarea en segundo plano finaliza o un temporizador programado con /schedule se cumple, el sistema despierta automáticamente al agente y le entrega el resultado.
